1. src/rbd.ts — Mount-directory ownership: add `existsSync(path: string): boolean` to the injected FileSystem type (default: real fs). In mount(device, mountPoint): before mkdirSync(recursive: true), record whether the directory already exists via existsSync. If the mount command fails, remove the directory with best-effort rmdirSync ONLY when this call created it, logging a cleanup failure with console.error without replacing the original error. Still throw the SAME wrapped error as today: `mount command failed with code <code>: <message>` (existing tests expect this exact message).
2. src/app.ts — VolumeDriver.Mount ownership rule (track ownership in local variables of the handler, NOT from isMapped after the fact): if isMapped(name) returned a device, the request does not own the mapping; if it returned null and the request's rbd.map(name) resolved successfully, the request owns the mapping. If rbd.mount then fails, best-effort rbd.unMap(name) only when owned; log cleanup failures with console.error and never let them replace the original error. The mountPointTable must not contain an entry for the volume afterwards. Return the ORIGINAL error in Err (as today).
3. src/app.ts — VolumeDriver.Create rollback (current sequence: create → map → makeFilesystem → unMap): if rbd.create fails, do nothing else (the image may be someone else's existing image); if create succeeded but map fails, best-effort rbd.remove(name) only (NO unmap — the request owns no mapping); if map succeeded but makeFilesystem fails, best-effort rbd.unMap(name) then best-effort rbd.remove(name); if create/map/makeFilesystem all succeeded but the FINAL unMap fails, do NOT roll back — no remove, no retry — because the image is complete and formatted and must be kept; return the unMap error in Err exactly as today (the image stays mapped; a later Mount finds it via isMapped). Return the ORIGINAL error in Err in all failure cases.

### coder (narrative)

I implemented best-effort rollback in docker-volume-rbd: rbd.mount now records whether the mount directory pre-existed via a new injectable existsSync and only rmdirs a directory it created, and app.ts tracks per-request ownership (a successful map after isMapped returned null, or whether create/map/mkfs succeeded) to decide what to roll back. The trickiest part was the Create sequence: the spec requires four distinct outcomes, so I used three booleans (createdImage, mappedImage, madeFilesystem) rather than inferring from command order — notably no rollback at all when the final unMap fails, since the image is already complete and formatted. Node was missing, so I loaded the setup-node skill and reused /tmp/node-v24 with pnpm via Corepack before installing with --frozen-lockfile. I added a small cleanupBestEffort helper so a throwing cleanup is logged rather than replacing the original error, and wrote 13 new node:test cases covering every rollback path, the no-rollback case, cleanup failures, and the created-vs-pre-existing mount directory. pnpm run build and the full pnpm test run (83 tests, 0 failures) both passed, and the change set is limited to the four allowed files, committed as 75d6a5e.
